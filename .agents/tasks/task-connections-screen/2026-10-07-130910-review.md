# Connections screen — Flutter Web

The Connections screen adds a three-tab UI (My Connections, Requests, Find Students) to the CampusCore web app. It wires all six connection-related API endpoints through `ApiConstants`, uses `FutureProvider.autoDispose` for data fetching, and separates profile fetching into a family provider with a guaranteed non-throwing fallback. The routing change in `app_router.dart` is correct and non-breaking. The implementation is generally clean and matches project conventions.

**Watch for:** (1) `_removeConnection` does not invalidate `pendingSentProvider` — if it's used as the "Reject" action on received requests, sent-request state stays stale after rejection. (confirmed) (2) `connectionRequest`, `connectionsPendingReceived`, `connectionsPendingSent` are declared as mutable `static String` fields, not `const` — they can be reassigned at runtime. (confirmed) (3) The Find Students tab's error state has no retry button — the user cannot recover from a transient failure without navigating away and back. (confirmed)

**Verdict**: APPROVED

---

## High-level view

All three tabs are implemented and functional. `connectionsProvider`, `pendingReceivedProvider`, and `pendingSentProvider` map correctly to their `ApiConstants` paths. `userProfileCacheProvider` wraps every network call in a try/catch and returns a named fallback instead of propagating errors, which is the right pattern for a dependent card fetch.

The action helpers all guard against double-taps (`_actionLoading[key] == true` check before proceeding), clean up loading state in `finally`, and invalidate the correct providers on success — with one exception: `_removeConnection` invalidates `connectionsProvider` and `pendingReceivedProvider` but not `pendingSentProvider`. This matters because `_removeConnection` is reused as the "Reject" callback in `_RequestsTab` for received requests, but `pendingSentProvider` is a separate list that wouldn't be stale in that path. The real gap is narrower: if the backend uses the same DELETE endpoint to reject received requests (which it does, per the API contract), then `pendingReceivedProvider` invalidation covers it. The missing `pendingSentProvider` invalidation in `_removeConnection` is only a gap when called from a context where a sent request is being removed — which isn't currently wired, since only `_cancelRequest` handles sent-request removal and it correctly invalidates `pendingSentProvider`. So this is a latent hazard rather than a current bug.

The mutable `static String` fields in `ApiConstants` are a style issue. They're currently only read, but the lack of `const` means a future edit could accidentally reassign them and affect global state. They should be `static const String`.

The Find Students tab's error state renders a centred `Text` with no retry affordance. Every other error path in the screen uses `_ConnErrorWidget` with a Retry button; this one breaks that pattern and leaves the user unable to recover without navigating away.

<details>
<summary>Issues (3)</summary>

1. **Mutable ApiConstants fields** — `connectionRequest`, `connectionsPendingReceived`, and `connectionsPendingSent` are declared `static String` (mutable) rather than `static const String`. Change all three to `static const String` in `api_constants.dart`.

2. **Find Students error state missing retry** — the `.error` branch in `_FindStudentsTab` renders a plain `Text` with no way to retry. Replace it with `_ConnErrorWidget` (passing `() => ref.invalidate(_findStudentsProvider(searchQuery))` as `onRetry`) to match every other error path in the screen.

3. **`_removeConnection` does not invalidate `pendingSentProvider`** — currently not a live bug (it's only called as Reject on received requests and Remove on accepted connections), but if a future code path reuses it for cancelling sent requests it will leave the Sent Requests list stale. Add `ref.invalidate(pendingSentProvider)` to `_removeConnection` for completeness.

</details>

<summary>Details</summary>

### Mutable static fields in ApiConstants

Three of the new constants in `api_constants.dart` are declared as mutable static fields:

```dart
static String connectionRequest = '/connections/request';
static String connectionsPendingReceived = '/connections/pending/received';
static String connectionsPendingSent     = '/connections/pending/sent';
```

Unlike the others (`connections` is `const`, and the methods return `String` literals), these three can be reassigned. The side effect of an accidental assignment would be silent and global. `static const String` is the right declaration for string constants that never change.

### Find Students error recovery

`_FindStudentsTab` handles its `.error` branch with:

```dart
error: (e, _) => const Center(
  child: Text(
    'Could not search. Please try again.',
    style: TextStyle(fontFamily: 'Nunito', color: AppColors.textHint),
  ),
),
```

There's no action the user can take from this state. Every other error path in the screen (`_MyConnectionsTab`, both sections of `_RequestsTab`) uses `_ConnErrorWidget` which renders a Retry button calling `ref.invalidate(...)`. The `_findStudentsProvider` accepts a `String` family param, so the retry call would be `ref.invalidate(_findStudentsProvider(searchQuery))`. Since `_FindStudentsTab` is a `ConsumerWidget`, `ref` is available.

### Provider invalidation coverage

| Action | Providers invalidated |
|---|---|
| `_sendRequest` | `pendingSentProvider`, `connectionsProvider` |
| `_acceptRequest` | `pendingReceivedProvider`, `connectionsProvider` |
| `_removeConnection` | `connectionsProvider`, `pendingReceivedProvider` |
| `_cancelRequest` | `pendingSentProvider` |

The table is complete for current call sites. `_removeConnection` is currently wired to two buttons: "Remove" in `_MyConnectionsTab` and "Reject" in `_RequestsTab`. Both are received/accepted contexts where `pendingSentProvider` is irrelevant, so there's no observable staleness today.

### Null safety and force-unwraps

`currentUserProvider` is read as `ref.watch(currentUserProvider)?.id` throughout, with the null-conditional operator. `userProfileCacheProvider` catches all exceptions and returns a named fallback. `_actionLoading[key] == true` is used consistently — no `!` unwrap on the map value. No force-unwraps on nullable values were found.

### Style compliance

All color references resolve to `AppColors` constants. All custom `TextStyle` declarations include `fontFamily: 'Nunito'`. `AppColors.primary.withValues(alpha: 0.15)` and `AppColors.info.withValues(alpha: 0.1/0.3)` use the non-deprecated form throughout. No hardcoded hex strings appear in the screen file.

### Route wiring

`/connections` in `app_router.dart` correctly maps to `ConnectionsScreen()`. The `ComingSoonScreen` import is retained for `/notifications` and `/leaderboard`. No unused imports are present in either file.
